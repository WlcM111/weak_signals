# Отчёт о проверках — сервис analyzer

Дата: 2026-09-16. Версия контрактов 1.0.0. Отчёт различает **выполненные** проверки и то, что
**не выполнялось** из-за ограничений среды сборки: сеть отключена, Docker и PostgreSQL недоступны,
пакеты `grpcio`, `psycopg`, `torch`, `sentence-transformers`, `pytest` не установлены. Ничего из
невыполненного не выдаётся за проверенное.

## Что выполнено

| Проверка | Команда | Результат |
|---|---|---|
| Юнит-тесты analyzer | `python -m unittest discover -s services/analyzer/tests/unit -t .` | **191 тест, PASS** |
| Юнит-тесты collector (регрессия после правок `ws_common`) | `python -m unittest discover -s services/collector/tests/unit -t .` | **142 теста, PASS** |
| Компиляция всех модулей | `py_compile` по 150 файлам | **PASS** |
| Соответствие кода контрактам `.proto` | `python tools/check_proto_conformance.py` | **PASS** (по 6 RPC у обоих сервисов, 5 перечислений у каждого, 39 сообщений) |
| Соответствие SQL схемам БД | `python tools/check_sql_conformance.py` | **PASS** (collector: 7 таблиц / 27 SQL-констант; analyzer: 7 таблиц / 24 SQL-константы) |
| Негативный контроль чекеров | внесены заведомые ошибки (`predicted_trendX`, `documents_inputX`) | обе **обнаружены**, после отката снова PASS |

Юнит-тесты работают на **настоящем артефакте модели**: фикстура `tests/model_fixture.py` обучает
маленькую логистическую регрессию, сохраняет `scaler/classifier/calibrator` через joblib, пишет
`centroids.npz`, `rules.json` и `manifest.json` с контрольными суммами. Проверяются реальная
загрузка через `FileSystemModelStore` (включая отказ при повреждённой sha256), реальный скоринг и
вычисление вкладов признаков.

### Что именно покрыто юнит-тестами

- **Признаки (25)**: лексические на синтетических текстах, коллекционные с известными долями,
  энциклопедические, эмбеддинговые; шкала `lexicon_rate` и её границы; значения «пустой коллекции».
- **Правила исключения (8)**: таблица «условие → решение/причина» для каждого правила, границы
  порогов (строгие и нестрогие неравенства), порядок применения, пороги из `rules.json`,
  обобщение правила единственного источника параметром `min_evidence_documents`.
- **Решение по модели**: `decide_by_score` по всем четырём веткам, объяснения (русский текст,
  порог, два главных вклада, лимит 500 символов), направления вкладов с полосой ±0.05.
- **Кластеризация**: три синтетические группы дают три кластера, near-dup с приоритетом
  доверенности и даты, «прочее» для мелких кластеров с исключением для одиночного HIGH-документа,
  отбор `max_candidates` по размеру × релевантности.
- **Ключевые фразы**: n-граммы без стоп-слов по краям, MMR (проверена арифметика λ = 0.7),
  запасная метка кластера.
- **Доказательства**: топ по близости, гарантия источника HIGH/MEDIUM, сниппеты ≤ 600 символов
  с ключевой фразой.
- **Реестр признаков**: 25/24, порядок, клиппинг, отказ на чужой версии схемы.
- **Инварианты сущностей**: `decision == WEAK_SIGNAL ⇔ rank ≥ 1`, лимиты длин, матрица переходов
  статусов анализа, ключ инвалидации кеша эмбеддингов.
- **Валидация контракта**: UUID, ключ идемпотентности, длины текстов, диапазоны параметров,
  keyset-токен (включая повреждённый).
- **Артефакт модели**: успешная загрузка, повреждённая sha256, подменённый файл, отсутствующий
  манифест, путь вне `model-store`, неверный `model_version_id`, порог вне диапазона.
- **Конвейер RunAnalysis целиком**: 10 документов трёх тематических групп → три кандидата с
  решениями WEAK_SIGNAL / MATURE (MARKET_LEADERS) / HYPE_OR_NOISE (MARKETING_DOMINANT), у каждого
  25 признаков, объяснение, доказательства с доверенным источником, корректная статистика;
  повторный анализ берёт эмбеддинги из кеша; near-dup убирает дубликат; правило энциклопедической
  зрелости; отказы (пустая коллекция, недоступный collector, фильтр релевантности, усечение);
  отмена между шагами и потеря аренды (в том числе при записи результата).
- **Сценарии**: активация модели (регистрация версии, отказ при несовпадении эмбеддера),
  StartAnalysis (предусловия, идемпотентность, лимит очереди, отсутствие модели), GetAnalysis,
  CancelAnalysis (идемпотентность), ListCandidates (порядок и keyset-пагинация), GetModelInfo,
  ScoreText (без обогащения, заглушки из манифеста, с обогащением, деградация при недоступном
  collector).

| Область | Причина | Что написано для получателя |
|---|---|---|
| Интеграция с PostgreSQL | нет Docker и БД | `tests/integration/` — 9 тестов на testcontainers: миграция (7 таблиц), идемпотентность, аренда и heartbeat, транзакционность записи (25 признаков × кандидатов), отказ при чужой аренде, замена кандидатов повторной попытки, инвалидация кеша, единственная активная модель, снятие истёкших аренд |
| Контрактные тесты gRPC | нет `grpcio` и сгенерированных стабов | `tests/contract/test_grpc_contract.py` — 9 тестов: 6 RPC, валидация, идемпотентность, пагинация, FAILED_PRECONDITION без модели |
| Реальные эмбеддинги e5 | нет `torch`/`sentence-transformers` и кеша HuggingFace | `adapters/outbound/e5_embedder.py` не исполнялся ни разу; скорость (≈ 40 док/с — допущение §24 HANDOFF) не замерялась |
| Клиент collector по gRPC | нет `grpcio` | `adapters/outbound/collector_grpc.py` не исполнялся; логика возобновления потока по `page_token` проверена только чтением кода |
| Сборка образа, compose, `/readyz`, метрики | нет Docker и сети | Dockerfile написан по образцу collector; не собирался |
| Генерация стабов `tools/gen_proto.sh` | нет `grpc_tools` | не запускалась; соответствие кода контрактам проверено статически |
| `ruff`, `mypy` | пакеты недоступны | не запускались; стиль соблюдался вручную (docstring у каждого модуля, класса и функции, длина строки ≤ 120) |
| Критерии приёмки §20 (демо-коллекция ≥ 300 документов, доля позитивов, исключённых правилами, время ScoreText) | требуют рабочего контура и обученной модели | не измерялись; проверяются после реализации trainer |

## Известные ограничения реализации

1. Активной модели в комплекте нет: trainer не реализован. Сервис поднимется, но останется
   не готов (`/readyz` 503) до появления артефакта в `model-store`. Все тесты используют
   фикстурную модель, обученную на синтетике, — её метрики ничего не говорят о качестве системы.
2. Пороги правил v1 взяты из §12.6 ТЗ и не калибровались на датасете: требование «правила 4–8
   исключают ≤ 5 % позитивов» не измерялось.
3. Шкала лексических признаков зафиксирована решением C-A2 (`docs/analyzer/DECISIONS.md`) и
   требует согласования с trainer: обучение обязано использовать ту же функцию.
4. `feature_defaults` для ScoreText хранятся в `rules.json`, а не в манифесте (C-A1) —
   согласование с trainer необходимо.
