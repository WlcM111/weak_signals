# Журнал решений и противоречий — сервис orchestrator

Обозначения: **C-O** — противоречие или неоднозначность комплекта, **D-O** — решение реализации.

## Противоречия

### C-O1. Формат тела ошибки: HANDOFF против OpenAPI

`HANDOFF_ORCHESTRATOR.md §14` описывает тело ошибки как `{error_code, message, details[],
correlation_id}`, а нормативная схема `Error` в `orchestrator.openapi.yaml` — как
`{code, message, request_id, details[], retryable}`.

**Решение.** Реализован формат OpenAPI: по `CONTRACT_RULES.md` нормативным источником для
серверной стороны HTTP является спецификация, а не текст задания. Идентификатор запроса
кладётся в `request_id` (в него же попадает `x-correlation-id`, если клиент его прислал).

### C-O2. Словарь `glossary_ru_en.yaml` принадлежит insight

§7.1 требует при отказе insight переводить запрос «по `glossary_ru_en.yaml`», но файл по
scaffold-структуре лежит в `services/insight/config/`, а insight ещё не реализован. Резервный
путь оказался бы неработоспособен ровно в том случае, ради которого он существует.

**Решение.** В `services/orchestrator/config/glossary_ru_en.yaml` лежит минимальная копия
словаря (около 50 терминов шести областей датасета). Путь перекрывается переменной окружения,
поэтому при появлении insight можно смонтировать общий файл. Отсутствие словаря не ломает
запуск: `Glossary.load` возвращает пустой словарь и запрос уходит в сбор как есть.

### C-O3. `GET /jobs/{id}/results` до появления снимка

OpenAPI объявляет для этого пути ответ `409` со схемой `Error`, но не называет код. §20.6 при
этом требует прогрессивную выдачу — `items_ready` должен расти во время `NARRATING`.

**Решение.** Результат доступен начиная со статуса `NARRATING` (и далее в терминальных
статусах, включая `CANCELLED` — частичный снимок остаётся полезным). До этого возвращается
`409` с кодом `RESULTS_NOT_READY`.

## Решения реализации

### D-O1. Обработчики HTTP отделены от FastAPI

Вся логика путей (валидация, идемпотентность, коды ошибок, пагинация) живёт в
`adapters/inbound/http/handlers.py` и возвращает пару «статус + тело». Роутеры FastAPI —
тонкие обёртки. Причина практическая: контракт HTTP проверяется 28 тестами без поднятия
uvicorn, а в среде сборки FastAPI и pydantic недоступны. Побочный эффект — тесты API работают
за миллисекунды и не зависят от версии веб-фреймворка.

### D-O2. Ссылки на коллекцию и анализ сохраняются до опроса

Первая реализация сохраняла `collection_id` после завершения стадии сбора. Тест отмены показал
дефект: при отмене в середине опроса ссылки ещё нет, и `CancelCollection` не вызывается —
сбор продолжает расходовать бюджет источников. Теперь стадия сообщает идентификатор колбэком
сразу после `StartCollection`/`StartAnalysis`, и он пишется в `jobs`. Это же делает повторную
попытку дешёвой: коллекция и анализ переиспользуются.

### D-O3. Откладывание вместо попытки при `RESOURCE_EXHAUSTED`

Отказ вышестоящего сервиса по нехватке ресурсов — не вина задания. Такие отказы помечены
`StageFailed(retryable=True)` и возвращают задание в `QUEUED` через 30 с **без** увеличения
`attempt`; счётчик откладываний ведётся по журналу `job_events` (`POSTPONED:*`) и ограничен
десятью. Так временная перегрузка collector не съедает три попытки задания.

### D-O4. Экстрактивный нарратив собирает orchestrator

Если insight недоступен, элемент выдачи всё равно формируется: описание берётся из первого
доказательства, объяснение — из `decision_explanation_ru` analyzer и трёх главных признаков,
статус помечается `FALLBACK_EXTRACTIVE`, провайдер — `none`. Требование ТЗ «не формировать
выдачу на знаниях языковой модели без подтверждённого поиска» здесь выполняется буквально:
текст целиком происходит из найденных источников.

### D-O5. Все признаки сохраняются, ключевых — пять

В снимок пишутся все признаки кандидата с `display_order` в порядке убывания модуля вклада
(порядок задаёт analyzer). `ResultItemSummary.key_predictors` — первые пять: список выдачи
остаётся читаемым, а полный разбор доступен на карточке элемента.

### D-O6. Прогресс считается по записанным данным

`JobProgress` собирается из `job_stats` и числа записанных `result_items`, а не из отдельного
счётчика в памяти воркера. Поэтому прогресс переживает перезапуск воркера и виден любому
процессу `api`.

### D-O7. Rate limit в памяти процесса

Скользящее окно по `sha256(ip + соль)` хранится в памяти `api`. §23 прямо запрещает вводить
Redis, а профиль нагрузки P1 (≤ 3 задания одновременно, один процесс api) делает
распределённый лимит избыточным. При масштабировании на несколько экземпляров лимит станет
приблизительным — это отмечено в отчёте о проверках.

### D-O8. Новые модули вне scaffold

`domain/rules.py` (правило COMPLETED/PARTIAL), `application/validation.py`,
`adapters/inbound/http/{handlers,presenters}.py`, `adapters/outbound/grpc/{clients,mappers}.py`,
`adapters/outbound/metrics.py`. Причина та же, что у остальных сервисов: правила и валидация не
должны жить в транспорте, а представления ответов проверяются отдельно от веб-фреймворка.

### D-O9. `orchestrator` в статических чекерах

`tools/check_proto_conformance.py` расширен понятием «сервис-клиент»: для orchestrator
проверяются поля конструируемых сообщений и совпадение перечислений (`Decision`, `TrustLevel`),
а проверка состава RPC пропускается — своего gRPC-сервиса у него нет.
`tools/check_sql_conformance.py` научился понимать столбцы с алиасами таблиц (`j.status`),
потому что `JOB_COLUMNS` описывает выборку с join.
