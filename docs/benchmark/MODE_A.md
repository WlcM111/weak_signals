# Режим А: повторяемая оценка выдачи

Этап 2 плана доработки (аудит A3). Задача — чтобы одно и то же задание можно было прогнать заново без сети и получить
ту же выдачу, а изменение одного параметра (абляцию) сравнить на тех же данных. Выбранный критерий приёмки аудита:
**повтор одной версии даёт ту же выдачу**.

## Что записывается на стенде

| Сервис | Таблица | Что | Выключатель |
|---|---|---|---|
| collector | `raw_responses` | итог каждого логического запроса адаптера: адрес без ключей, код отказа или сжатое тело ответа с SHA-256, время | `WS_COLLECTOR_TRACE_ENABLED` |
| collector | `document_events` | судьба каждого документа, выданного адаптером: `ACCEPTED`, `DEDUP`, `SOURCE_CAP`, `REJECTED` — с источником и фразой запроса | `WS_COLLECTOR_TRACE_ENABLED` |
| analyzer | `analysis_captures` | векторы документов и всех остальных вызовов эмбеддера (в порядке вызова), ответы Wikipedia, дата признаков свежести, настройки, воронка документов | `WS_ANALYZER_CAPTURE_ENABLED` |
| orchestrator | `job_traces` | стадии `job`, `expand`, `collect`, `analyze`, `narrate` (или `narrate_legacy`): пул, вердикты рубрики, вероятности, раунды доводки, отказы и причины, показанные карточки, остановка по сроку | всегда |
| insight | `llm_recordings` | полный текст промпта и ответа каждого вызова провайдера, ключ повтора, `job_id` задания | `WS_LLM_RECORD_ENABLED` |

Все выключатели по умолчанию включены. Запись промптов и ответов — решение владельца проекта от 03.10.2026: оно
заменяет правило §14.5 ТЗ «ни промпт, ни ответ не сохраняются» ради воспроизводимости. Журнал `llm_calls` по-прежнему
хранит только метаданные.

Сбой записи трассы не срывает задание пользователя: он пишется в журнал сервиса (`collection.trace_failed`,
`analysis.capture_failed`, `job.trace_failed`, `stage.narrate_rubric.trace_failed`, `llm.recording_failed`), а выгрузка
снимка отмечает неполноту в `manifest.json` (`issues`).

Объём записи на задание не измерялся на стенде. Оценка по составу: векторы анализа — от единиц до двух десятков МБ,
сжатые ответы источников — единицы МБ, записи LLM — до 1–2 МБ. Автоматической очистки этих таблиц нет.

## Снимок задания

`tools/benchmark/freeze.py` (только стандартная библиотека, запуск на машине со стендом из корня проекта) выгружает
для каждого задания каталог `ml/reports/benchmark/<время>/<тема>-<начало job_id>/`:

| Файл | Содержимое |
|---|---|
| `manifest.json` | задание, тема, время, версии (git HEAD и число незакоммиченных файлов, образы compose, версии промптов, модели LLM), `.env` без секретов, проблемы полноты, SHA-256 каждого файла |
| `job.json` | строка задания, элементы выдачи, их источники, исключённые кандидаты |
| `trace.json` | трасса orchestrator по стадиям |
| `collection.json`, `documents.jsonl`, `document_events.jsonl`, `raw_responses.jsonl` | коллекция, запуски адаптеров, документы как их видел analyzer, события документов, сырые ответы |
| `analysis.json`, `capture.json`, `vectors.npz` | анализ, кандидаты с документами, запись входов анализа, векторы |
| `llm_recordings.jsonl` | вызовы LLM задания |
| `model/`, `insight/prompts`, `insight/schemas`, `orchestrator_config/` | модель analyzer, промпты и схемы, модели orchestrator — скопированы из работающих контейнеров |

## Повтор

`python -m ml.benchmark replay` (в образе trainer) прогоняет на снимке анализ, рубрику, доводку и выдачу **тем же кодом
сервисов**. Подменены только внешние границы: эмбеддинги — векторами записи, Wikipedia — записанными ответами, LLM —
записанными ответами по ключу запроса (SHA-256 сообщений, схемы, лимита токенов и температуры), часы — датой записи.
Межсервисные вызовы идут через те же функции построения запросов и разбора ответов, что и gRPC, с сериализацией
сообщений туда и обратно. Что повтор идёт тем же путём, проверяет `ml/tests/test_benchmark_grpc_parity.py`: настоящий
gRPC-клиент orchestrator и настоящий сервер insight дают те же карточки, вердикты и запросы к модели.

| Статус | Значение |
|---|---|
| `IDENTICAL` | выдача повтора совпала с живой: ранги, кандидаты, названия, уверенность (с допуском 0,0001 — в базе она хранится с четырьмя знаками), статус текста, источники |
| `DIFFERENT` | повтор полный, но выдача другая — список различий в отчёте |
| `INCOMPLETE` | повтор обратился к тому, чего нет в записи (LLM, эмбеддинг, Wikipedia), или в снимке нет файла |
| `NOT_COMPARABLE` | живое задание остановлено сроком, или модель в снимке не совпала с моделью задания |

`--repeat 2` (по умолчанию) повторяет дважды и проверяет, что повторы совпадают между собой.

Абляция — `--set группа.параметр=значение`, группы `analyzer` (настройки анализа, например
`analyzer.min_candidate_query_sim=0.85`), `params` (параметры анализа, например `params.max_candidates=60`), `narrate`
(настройки отбора, например `narrate.rubric_pool=60`). Если абляция порождает новые запросы к LLM, их ответов в записи
нет — повтор честно получает `INCOMPLETE` со списком ключей.

## Воронка и режим Б

`python -m ml.benchmark funnel` строит по снимкам отчёт `funnel.md` и `funnel.json`:

- **Сбор.** Итог опроса каждого источника (B2-a): «не опрошен» (ноль HTTP-запросов при любом статусе), «опрошен,
  пусто», «есть документы», «частично», «отказ», «лимит частоты», «не завершён». Кроме того — доля успешных запросов
  по источнику и события документов. Окно дат, бюджет и размер корпуса — поля режима Б.
- **Анализ.** Почти-дубли, порог близости документа, одиночные кластеры, кластеры, отсечённые числом кандидатов.
  Кандидаты ниже порога близости кандидата (`LOW_QUERY_RELEVANCE`) — измерение гипотезы B4; решение принимается на
  этапе 3.
- **Отбор.** Пул и отсечённые пулом (отдельно — с `LOW_QUERY_RELEVANCE`), коды рубрики, добор, раунды доводки,
  отказы, остановка по сроку.

## Известные ограничения

1. Повтор начинается с документов коллекции: сам сбор не повторяется. Сырые ответы нужны для аудита отбраковки и
   для будущей пересборки документов.
2. Состояние цепочки LLM между заданиями не записывается. Если основной провайдер был выключен размыкателем до
   задания, повтор обратится к нему и получит «нет записи» — статус `INCOMPLETE`.
3. Кеш нарративов insight (резервная генерация по хешу входа) при повторе не используется. Если живое задание взяло
   нарратив из кеша, повтор получит «нет записи».
4. Порядок документов кандидата с одинаковой после округления до float32 близостью в живой БД не определён. Повтор
   берёт порядок, в котором их построил analyzer.
5. Внутренние повторы HTTP-клиента collector не пишутся по отдельности — только итог логического запроса.
6. Совпадение с живой выдачей на тестовых данных проверено тестами. На снимках стенда его подтверждает команда
   `replay` из инструкции этапа (ожидается `IDENTICAL`).
