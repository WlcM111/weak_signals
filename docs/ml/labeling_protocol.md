# Протокол разметки отрицательного класса

## 1. Зачем нужен отрицательный класс

Датасет организаторов содержит только положительные примеры: 100 технологий, которые методологи
признали слабыми сигналами. Классификатор нельзя обучить на одном классе, поэтому команда строит
отрицательный класс сама. От его качества зависит всё: если негативы отличаются от позитивов не
сутью, а способом написания, модель выучит стиль, а не методологию.

## 2. Состав по протоколу (§6.2 задания)

| Подтип | Целевая доля | Критерий |
|---|---|---|
| N-mature | 50 % | сформированный рынок старше 3 лет, стандарты или консорциумы, ≥ 3 крупных вендора, популярная статья в Wikipedia |
| N-hype | 30 % | преобладают пресс-релизы и блоги, нет научных и патентных источников, лексика «революционный / первый в мире» без данных |
| N-noise | 20 % | общие термины и названия дисциплин, не технологии; переупакованные известные технологии |

Обязательны ≥ 30 жёстких негативов — зрелые технологии из тех же шести областей, что и позитивы.
Области берутся из датасета: `industrial_ai`, `robotics`, `ai_infrastructure`, `fintech`,
`ai_security`, `edge`.

## 3. Фактический состав

Источник: `ml/data/labels/negatives_dev_b.yaml` (человекочитаемый список), из него команда
`build-negatives` собирает строки по `training_row.schema.json`.

| Показатель | Значение |
|---|---|
| Всего негативов | 125 |
| N-mature | 68 (54 %) |
| N-hype | 33 (26 %) |
| N-noise | 24 (19 %) |
| Областей | 6, по 20–21 строке |
| Строк без источника | 0 |

Доли отличаются от целевых на 4 п.п. в пользу зрелых технологий: жёсткие негативы важнее для
задачи (отделение слабых сигналов от зрелого рынка — прямое требование ТЗ), чем точное попадание
в пропорцию.

## 4. Формат строки

```json
{"row_id": "neg-0001", "group_id": "<слаг названия>", "origin": "team_negatives_v1",
 "title": "Название (english name)", "description": "2–3 нейтральных предложения о сути",
 "domain_tag": "ai_infrastructure", "label": 0, "label_kind": "MATURE",
 "source_urls": ["https://..."], "annotators": ["dev_b"], "annotation_agreement": null}
```

`label_kind`: N-mature → `MATURE`, N-hype и N-noise → `HYPE_OR_NOISE`. Подтип и обоснование
хранятся отдельно — в `ml/data/labels/annotations_dev_b.csv`, чтобы не расширять нормативную схему.

Описания пишутся нейтрально: без слов «революционный», «прорывной», «зрелый», «устаревший».
Оценочные маркеры в описании негатива — такая же утечка, как маркеры разметки в описании позитива.

## 5. Перекрёстная разметка — НЕ ВЫПОЛНЕНА

Протокол требует: два разработчика независимо составляют по 75 кандидатов, затем каждый
размечает список другого, считается каппа Коэна по `label`, условие приёмки — κ ≥ 0.7.

**Фактически выполнена только половина**: список составлен одним аннотатором (`dev_b`).
Второй аннотатор не размечал его, поэтому:

- `annotation_agreement` у всех строк пуст;
- каппа Коэна **не вычислена** — это прямое расхождение с критерием приёмки §20.1 задания;
- 20 позитивов, которые по протоколу перепроверяются обоими аннотаторами, не перепроверялись.

Инструменты для второй половины готовы и проверены тестами:

```bash
python -m ml.cli build-negatives                       # создаёт annotations_dev_b.csv
# второй аннотатор заполняет CSV с колонками row_id,label
python -m ml.cli build-negatives --second-annotation ml/data/labels/annotations_dev_a.csv
```

Команда печатает число сравнённых строк, каппу и список расхождений. Расхождения обсуждаются:
строка либо получает `annotation_agreement=resolved`, либо исключается из набора.

## 6. Источники

Для каждого негатива указана опорная ссылка. Для зрелых технологий это, как правило, статья
Wikipedia — она же служит объективным индикатором зрелости (правило 4 §12.6 ТЗ использует
возраст статьи и посещаемость). Для N-hype и N-noise ссылка указывает на статью о родовом понятии.
При перекрёстной разметке второй аннотатор обязан заменить или дополнить ссылки первичными
источниками там, где это возможно.

## 7. Что делать дальше

1. Провести перекрёстную разметку и зафиксировать каппу (блокирует критерий приёмки §20.1).
2. Выровнять описания негативов по длине с позитивами: сейчас позитивы 204–401 символ, негативы
   62–206, и это само по себе разделяет классы (см. раздел 7a отчёта об оценке).
3. Добавить 20–30 негативов, написанных в той же манере, что и колонка «Почему это слабый сигнал»,
   чтобы проверить устойчивость модели к стилю.
